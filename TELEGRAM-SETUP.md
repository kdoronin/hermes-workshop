# Telegram: подключение и проверка

Это поручение агенту на согласованной машине пользователя. Выполняй его после настоящего ответа модели в CLI, в рамках [полного цикла](ONBOARDING.md). На машине автора репозитория ничего не подключай. Чтение файла не разрешает создавать бота, переключать действующую службу или отправлять сообщения.

Официальные источники: [Telegram Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/telegram), [шлюз](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/), [quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart). Перед выполнением прочитай их и справку установленной версии; названия команд ниже служат ориентирами.

## 1. Согласуй маршрут

Одним блоком, не больше пяти коротких вопросов, уточни только недостающее:

1. Используем существующего бота или создаём нового?
2. Какой Telegram-аккаунт владельца получает доступ?
3. Тестируем в личном чате или в конкретной согласованной теме?
4. Запускать временно в foreground или настраивать постоянную службу с автозапуском?
5. Есть ли у существующего бота другой gateway, хостинг или webhook?

Зафиксируй машину, пользователя ОС, активный профиль и несекретную идентичность бота. Не переносить токен в другой профиль без отдельного разрешения. Отказ от Telegram останавливает полный цикл со статусом «незавершено»; CLI может работать, но финального успеха нет. При отсрочке сохрани место продолжения.

## 2. Новый или существующий бот

### Новый

Попроси пользователя открыть **официального @BotFather** в Telegram, проверить аккаунт и отправить `/newbot`. Он выбирает отображаемое имя и свободный уникальный username, который заканчивается `bot`. После успешного создания пользователь сохраняет токен локально и вводит его только в защищённый штатный wizard. Не проси переслать ответ BotFather агенту.

Если пользователь не может выполнить этот шаг, дождись его участия. Не создавай бота в аккаунте автора или агента. Произвольный аккаунт с похожим именем не подходит.

### Существующий

Не вызывай `/newbot` и не создавай дубликат. Сверь выбранный username/несекретный bot ID с пользователем и, после защищённой настройки, с аутентифицированной идентичностью бота. Установи, кто сейчас получает обновления. Нельзя считать отсутствие локального процесса доказательством отсутствия удалённого потребителя.

Для переноса согласуй окно остановки, точный прежний процесс/сервис, новый профиль и возврат. Останови только согласованный старый потребитель, затем запускай новый. **Один токен — один владелец polling**, включая другие машины, профили, контейнеры и ручные процессы. Не запускай foreground поверх службы. При конфликте опроса останови свой новый процесс и найди владельца; не убивай чужие процессы вслепую.

До первого запуска узнай состояние webhook безопасным средством, которое не выводит токен: штатный интерфейс или локальная проверка с секретом, прочитанным внутри процесса. Не помещай Bot API URL с токеном в shell, историю или отчёт. Если webhook есть, не вызывай `deleteWebhook`, не меняй URL и не запускай способ, который автоматически удалит его, без явного согласия владельца на переключение. Неизвестный владелец или невозможность безопасной проверки — блокировка, а не разрешение попробовать запуск. Отдельно согласуй судьбу накопленных обновлений; старые команды могут иметь побочные эффекты.

### Create with QR: только если уже доступно

Новые dashboard/desktop могут предлагать Messaging → Telegram → **Create with QR**. Предложи этот маршрут только при наличии кнопки в уже установленном интерфейсе. Не устанавливай GUI ради QR. Этот путь может создать бота, определить ID, записать секреты и перезапустить gateway: сначала согласуй эти действия и проверь безопасность до автоматического запуска. Для существующего бота используй подключение существующего, а не Create. Если интерфейс не даёт подтвердить owner-only доступ до запуска, вернись к ручному маршруту. QR, ссылки авторизации и коды не сохраняй в журнал или переписку. После QR обязательны те же проверки доступа и ответа.

## 3. Секрет и доступ до запуска

1. На целевой машине, в подтверждённом профиле прочитай `hermes --help`, `hermes gateway --help`, `hermes gateway setup --help`. Проверь способ выбора профиля по этой версии. Все последующие команды выполняй в этом же контексте; пример без флага профиля не разрешает уйти в default.
2. Получи **numeric owner user ID**, а не username, bot ID или ID группы. Пользователь может посмотреть его через способ из официальной инструкции (например, @userinfobot, учитывая передачу ID этому сервису). Не угадывай число. Подтверди, что оно принадлежит выбранному владельцу.
3. Запусти штатный `hermes gateway setup`, выбери Telegram. Секрет вводит пользователь непосредственно в локальный wizard без записи ввода агентом; для удалённой машины нужен защищённый локальный терминал на ней. Запрет: токен в чате, shell argv, командной строке `config set`, URL команды, логах, записи экрана, JSON-журнале и Git. Не запускай запись терминала, tracing или verbose вокруг ввода. Если маскировка/приватный ввод недоступны, попроси человека выполнить только этот шаг вне записываемого сеанса, затем продолжи.
4. **До запуска** проверь, что `TELEGRAM_ALLOWED_USERS` содержит только согласованный numeric owner ID. Не печатай `.env` целиком. Проверь эффективные настройки доступа, включая переопределения профиля/службы; пустой список не принимай. Запрещены `*`, allow-all и `GATEWAY_ALLOW_ALL_USERS=true`; не ослабляй доступ ради диагностики. Непредусмотренные дополнительные пользователи, группы и ранее выданные разрешения требуют разбора до старта. Проверь групповые allowlist, pairing, роли и `guest_mode` по этой версии: они не должны давать посторонним обход owner-only. Для первого теста предпочти личный чат. Не отключай BotFather privacy mode, не добавляй бота в группы и не выдавай admin-права ради прохождения теста; групповой сценарий согласуй отдельно с минимальными правами. Подтверждение «owner-only, проверено» сохраняй без самих личных идентификаторов.
5. Проверь адреса конфигурации и хранилища секретов активного профиля, ограниченные права локальных файлов и идентичность бота, не раскрывая секрет. Не выгружай диагностический архив с секретами. При утечке останови настройку, предложи отозвать токен в BotFather и безопасно заменить его; не цитируй утёкшее значение.

## 4. Gateway: выбранный режим работы

Сверь доступные подкоманды по `hermes gateway --help` и справке каждой используемой команды. Типичные варианты: `hermes gateway run` для foreground; `install`, `start`, `status`, `stop`, `restart` для службы. Это не универсальный скрипт: если версия использует другой синтаксис, выполняй её документированный вариант.

- **Foreground:** запускай один процесс в согласованном терминале; службу и автозапуск не устанавливай. Объясни, что после закрытия терминала/SSH, сна или выключения бот может перестать работать. Не отмечай автозапуск проверенным.
- **Постоянная служба:** отдельно согласуй установку и политику автозапуска, затем выполни поддерживаемые для ОС команды. Проверь, что служба использует нужные пользователя, профиль и executable. Установка службы, её работа сейчас, восстановление после выхода и после перезагрузки — разные проверки. Не обещай непроверенное восстановление.

Проверь процесс и подключение Telegram. Если шлюз не готов, изучай только отфильтрованные несекретные ошибки. Не меняй firewall, proxy, webhook, модель или allowlist без соответствующего выбора. Согласуй простой заранее; собственный gateway не должен завершать сам себя посреди установки — управляй им из отдельного локального терминала/агента.

## 5. Первый настоящий тест

1. Попроси владельца открыть **именно выбранного бота** и отправить `/start`, затем новую уникальную нейтральную фразу, например «Проверка <случайная метка>: придумай короткое предложение про маяк и включи метку в ответ». Метку каждый раз создавай заново. Не используй личные данные.
2. Дождись ответа **модели**, а не только служебного приветствия, `/help`, реакции или typing. Сопоставь вход, ответ и несекретную запись сессии/вызова провайдера; мок, старый ответ или фиксированное эхо не подходят. Если наблюдать чат нельзя, запроси подтверждение конкретного ответа пользователем и доступные несекретные ссылки; не выдумывай message ID.
3. Сверь бот, целевую машину/профиль, владельца и согласованный чат/тему. Запиши ссылку на разрешённый локальный протокол проверки, время и результат без токена и личного содержимого. Отметь `telegram_owner_access` только после проверки настроек доступа и приёма владельца, `telegram_roundtrip` — после ответа модели.
4. `/sethome` необязателен. Выполняй его только после согласия на **точный чат и тему**, откуда будет команда, и последующего чтения результата маршрутизации. Существующий адрес сохраняй, пока пользователь не одобрит замену. При темах проверь thread ID и отдельные переопределения cron по установленной версии. Пробная доставка — отдельное согласованное действие.

Не требуется просить незнакомца писать боту ради отрицательного теста. Проверь запрет посторонних по эффективной политике; дополнительный тест вторым контролируемым аккаунтом возможен только по согласованию. Ошибка модели или доставки оставляет цикл незавершённым.

## 6. После модулей

Вернись в [ONBOARDING.md](ONBOARDING.md), выполни выбранное. После согласованного перезапуска gateway в прежнем режиме и новой сессии повтори тест **из Telegram** с другой уникальной меткой. Проверь доступность нужных инструментов именно Telegram: `platform_toolsets.telegram` может отличаться от `platform_toolsets.cli`, а навыки сами по себе не выдают доступ к инструментам. Не копируй весь CLI-набор автоматически.

После перезапуска проверь фактический процесс, executable, версию и профиль: запиши `runtime_after_modules`. Только фактический повторный ответ модели после применения изменений с проверенным provider/model даёт `model_reply_after_modules` и `telegram_after_modules`. Эти две проверки могут ссылаться на один наблюдённый ответ из Telegram, дополнительный платный запрос не нужен. Если модулей не выбрано, проверка после зафиксированного выбора и согласованного перезапуска всё равно нужна. Если пользователь отложил перезапуск, тест или авторизацию, сохрани блокировку и точное действие продолжения; итог «готово» запрещён.
